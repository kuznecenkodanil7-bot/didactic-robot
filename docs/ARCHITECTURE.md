# Архитектура и границы безопасности

## Поток входящего сообщения

1. Vanilla принимает серверный пакет обычным сетевым кодом.
2. Vanilla вызывает `ChatHud.addMessage(Text, MessageSignatureData, MessageIndicator)`.
3. `ChatHudMixin` копирует исходный `Text` в `ChatManager`.
4. К display-копии применяются локальные emoji-замены, linkify и зарегистрированные API-трансформеры.
5. Исходный объект хранится отдельно и никогда не отправляется обратно серверу.
6. Vanilla продолжает добавление сообщения в свой внутренний список.
7. На этапе `ChatHud.render(...)` стандартная отрисовка заменяется собственным `ChatRenderer`.

Благодаря этому серверные плагины уже успевают сформировать окончательный компонент сообщения, а их цвета, префиксы и события не приходится угадывать по названию плагина.

## Исходящая строка

`ChatScreenMixin` меняет только аргумент `String` в `ChatScreen.sendMessage`. Затем выполняется штатная ванильная логика команды или сообщения. Никаких дополнительных пакетов, повторных отправок и обходов лимитов нет.

Быстрый ответ `F4` также вызывает обычный `ClientPlayNetworkHandler.sendChatMessage` ровно один раз.

## Mixin-точки

- `ChatHud.addMessage(Text, MessageSignatureData, MessageIndicator)`
- `ChatHud.render(DrawContext, TextRenderer, int, int, int, boolean, boolean)`
- `ChatHud.clear(boolean)`
- `ChatHud.removeMessage(MessageSignatureData)`
- `ChatScreen.sendMessage(String, boolean)`
- методы ввода и render экрана чата для click/hover/scroll

Миксины не заходят в packet decoder, connection pipeline или античит-чувствительные обработчики движения.

## Совместимость компонентов

Кэш содержит `Text`, а не только `String`. Поэтому сохраняются:

- вложенные siblings;
- RGB и legacy-цвета после преобразования сервером;
- `ClickEvent`;
- `HoverEvent`, включая `ShowItem`;
- insertion;
- нестандартные шрифтовые стили, если ресурс доступен клиенту.

Парсер имени используется только для аватарки, группировки и контекстного меню. Ошибка парсинга не повреждает само сообщение: оно просто считается системным.

## Производительность

- основной кэш ограничен `maximumMessages`, жёсткий потолок 10 000;
- рендер берёт immutable snapshot;
- журнал пишется одним daemon-потоком;
- skin textures получает ванильный cache, загрузка не блокирует render thread;
- regex компилируются только при изменении списка;
- HTTP-перевод выключен по умолчанию и выполняется через `HttpClient.sendAsync`.

## Почему нет межклиентских статусов

Состояния `AFK`, `в меню` и наличие мода у другого игрока нельзя надёжно узнать только из стандартного чата. Любая честная реализация требует серверного посредника или пользовательского канала. Проект намеренно выбирает отсутствие этой функции вместо нарушения требования «не отправлять кастомные пакеты».
